## 1. README 構成（ポートフォリオ向け）

人に見せる前提の丁寧な構成にする。以下を基本セットとし、プロジェクトの性質に応じて過不足を調整する。

1. タイトル・一言概要
2. デモ（スクリーンショット / GIF / 公開 URL など、視覚的に伝わるもの）
3. 背景・課題（なぜ作ったか）
4. 主な機能
5. アーキテクチャ図・技術スタック一覧
6. 技術選定理由（詳細は該当する `decisions/` の ADR にリンク）
7. セットアップ手順
8. 使い方
9. テストの実行方法（テストコード・CI がある場合のみ）
10. 今後の展望・既知の制約

> `## 6. 技術選定理由` は結論だけ書き、詳しい検討過程は ADR に逃がす。README が長くなりすぎるのを防ぐため。
> README は外部向けの完成形のみとする。自分用の詳しい設計メモ・試行錯誤ログは `notes/` に置き、README には含めない。

## 2. テスト方針

- 主要ロジック（ビジネスロジック・データ変換・計算処理など）には単体テストを書く
- UI・インフラ寄りの部分（画面表示そのもの、デプロイ設定など）は対象外でよい
- `pytest` を基本とする
- CI（GitHub Actions）で `ruff check` と `pytest` を実行する

---

## 3. Design Decision（ADR）運用ルール

技術選定や設計判断のうち、「あとで振り返ったときに理由を忘れそうなもの」を記録する。

- 形式: 軽量 ADR。1 決定 = 1 ファイル
- 置き場所: プロジェクト直下の `decisions/` ディレクトリ
- ファイル名: `NNNN-短いタイトル.md`（例: `0001-use-sqlite-over-postgres.md`）
- Status の種類: `Proposed` / `Accepted` / `Deprecated` / `Superseded by NNNN`
- 起票タイミング: 実装に着手する前、選択肢を比較して決めた直後
- テンプレートは `decisions/0000-template.md` に置いてある

### テンプレート

```markdown
# NNNN. タイトル

- Status: Proposed
- Date: YYYY-MM-DD

## Context
どんな背景・制約でこの判断が必要になったか。

## Decision
何を決めたか（結論を先に一文で）。

## Consequences
この決定によって生まれるメリット・トレードオフ・今後の制約。
```

## 4. デプロイ・公開方針の判断基準

プロジェクトを始める際、最初に以下を検討し、結論を最初の ADR として残す。

- 誰に見せたいか（採用担当者などに見せたい → 公開デモが望ましい / 自分専用ツール → ローカル完結で十分）
- 継続的に使うか（作って終わりか、日常的に稼働させ続けるか）
- 運用コスト（クラウド利用料が発生するか、無料枠に収まるか）
- 公開可否（スクレイピング・API 利用規約・第三者データの扱いなど、コードや成果物を公開すると規約違反や迷惑になるリスクがないか）

判断結果の例:

| 方針 | 該当ケース |
|---|---|
| GitHub 公開 + デモ URL 公開 | 採用面接などで見せたい、UI が主役のプロジェクト |
| GitHub 公開まで | コードと README が読めれば十分、常時稼働のデモは不要 |
| ローカル完結 | 自分専用の分析ツール・ライフログ収集など |
| 非公開（コード・成果物とも外部に出さない） | スクレイピングなど利用規約上グレーな手段を含み、公開すると問題になりうるもの |
